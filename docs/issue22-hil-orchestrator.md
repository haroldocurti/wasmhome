# Issue #22 HIL orchestrator

`tools/issue22_hil_orchestrator.py` is the single user-mode entry point for the
16-row preliminary #22 physical campaign. It supersedes the manual `runner`
and HTTP-log collection steps in the earlier implementation note. It does not
run the 72-row #23 matrix.

## Required gates

The orchestrator stops before opening the serial port unless all of these
inputs validate:

1. A #20 timeout proof JSON using schema
   `wasmhome-issue20-frozen-timeout-v1`, with `status: "frozen"`,
   `functional_timeout_frozen: true`, a supported integer timeout, and a
   protocol SHA-256.
2. The exact 16 MiB baseline image and its SHA-256 that #20 accepted. The
   image must match the repository partition table. The connected ESP32-S3
   must have the registered MAC, 16 MiB flash, and the same full-flash hash.
   The orchestrator never promotes a newly read device image to baseline.
3. A profile manifest using schema
   `wasmhome-issue22-bootstrap-profiles-v2`, the frozen #20 timeout, and
   native/interp/aot v1 app images, their same-build bootloaders, sdkconfig and
   generated `bootloader/config/sdkconfig.h`, all with recorded SHA-256 values. Each app BIN
   must include the `WASMHOME_ISSUE22_BUILD_V2` marker generated by CMake from
   that build's actual sdkconfig and CA bytes. The validator extracts the
   compiled profile, timeout, IP, port, TLS name, CA digest, rollback flag and
   sdkconfig digest from the BIN and
   compares them to the manifest; it also checks the exact CA PEM is embedded
   in the image. Both config artifacts must declare the same app rollback mode;
   native requires it enabled, while module profiles may retain it disabled.
   All configs must target ESP32-S3, 16 MiB flash and table offset 0x8000. Bootloader images
   must be complete S3 images smaller than 0x8000. The offline validator checks
   every segment, checksum, appended SHA-256, exact EOF, executable entrypoint
   and the pinned IDF v5.2.6 bootloader description. A header-only file, unknown
   trailer, corrupted image or application masquerading as a bootloader is
   rejected. Editing only the JSON cannot
   make a stale app pass. Schema v1 manifests and V1 BIN markers are rejected.
4. Both firmware endpoints (normal signed sequence-2 provisioning and
   resilience fixtures) must match the orchestrator's CT IPv4 address, HTTPS
   port `18445`, TLS name and shared CA hash. CMake rejects different
   `WASMHOME_UPDATE_SERVER_*` and `WASMHOME_RESILIENCE_FIXTURE_SERVER_*`
   settings. The V2 app marker records both; the profile manifest must contain
   identical `endpoint` and `update_endpoint` records. Current packages built for `:8445` fail
   this gate. Rebuild and re-sign the campaign for `:18445`; the orchestrator
   will not terminate or replace a listener on `:8445`.
5. A valid TLS certificate chain, a private TLS key, and the signed artifact
   set. The package must contain the registered v2/sequence-2 releases for all
   three scenarios. The firmware hashes in
   `tools/resilience_hil_runner.py` must be updated together with the final
   post-#20 builds; the earlier local package hashes are preliminary.
6. The nine closed negative fixtures and all six payload/manifest files from
   the signed sequence-2 package. The CT server validates one merged allowlist
   containing 24 exact routes before binding.
7. The provisioned `wasmhome` SSH identity and pinned known-hosts file. The
   default connection uses `wasmhome@192.168.0.138` with
   `HostKeyAlias=192.168.0.138`, strict host-key checking and batch mode.
8. An ordinary local user with access to `/dev/ttyACM0`, Python/esptool, and
   the UDP observer interface. Root, `sudo`, systemd linger, system units and
   root access to Proxmox are not part of the workflow.

These are hard gates. In particular, no #22 physical run may start until #20
has frozen the timeout and published its accepted baseline. The implementation
does not manufacture either artifact from current device state.

## CLI

Run the no-hardware preflight after the timeout, baseline, profile, OTA and TLS
artifacts are available. Supply the local addresses from the current bench
network; the firmware endpoint address is the CT address reachable by the
ESP32-S3.

```sh
python3 tools/issue22_hil_orchestrator.py --action check \
  --profiles /path/to/issue22-profiles.json \
  --timeout-proof /path/to/issue20-timeout-proof.json \
  --accepted-baseline /path/to/issue20-accepted-flash.bin \
  --accepted-baseline-sha256 <64-hex-sha256> \
  --ota-package-root /path/to/signed-issue22-package \
  --ota-signing-public /path/to/ota-signing.pub \
  --fixture-root /path/to/issue22-fixtures \
  --fixture-trusted-public /path/to/fixture-trusted.pub \
  --fixture-untrusted-public /path/to/fixture-untrusted.pub \
  --aot-toolchain-id <registered-toolchain-id> \
  --tls-ca /path/to/issue22-ca.pem \
  --tls-certificate /path/to/issue22-server.crt \
  --tls-private-key /path/to/issue22-server.key \
  --server-name wasmhome-issue22.test \
  --server-ip 192.168.0.138 --https-port 18445 \
  --device-ip <esp32-lan-ip> --bind-ip <host-lan-ip> \
  --serial-port /dev/ttyACM0 --expected-mac dc:b4:d9:0b:22:e4 \
  --esptool /path/to/esptool.py \
  --output-root /path/to/private/issue22-campaign
```

`check` is static and does not connect to CT or access the board. For the first
physical run, repeat those arguments with `--action run`. `--max-slots` limits
each invocation to 1–16 rows; it never changes the plan from the exact 16-row
#22 preliminary scope. Defaults are a 16-row run, HTTPS port 18445, SSH target
`wasmhome@192.168.0.138`, SSH port 22, and the already provisioned key paths
under `~/.ssh/wasmhome-ct107-hil` and
`~/.ssh/wasmhome-ct107_known_hosts`.

The complete CLI is available with `python3 tools/issue22_hil_orchestrator.py
--help`. Run/check options and their defaults are:

| Option | Default / use |

`--action resume` restores the exact saved options and fingerprints from the
campaign journal; do not pass a second set of build or network settings. The
`recover` action takes the same saved values and requires the registered serial
port, esptool executable and MAC already stored there.

The first run saves its validated configuration and input fingerprints in the
private campaign journal. After a process or host crash, use only:

```sh
python3 tools/issue22_hil_orchestrator.py --action recover \
  --output-root /path/to/private/issue22-campaign
python3 tools/issue22_hil_orchestrator.py --action resume \
  --output-root /path/to/private/issue22-campaign
```

`recover` reloads the campaign configuration and verifies the saved accepted
baseline and registered board identity. If the durable journal says a flash
write phase began, it restores all 16 MiB and verifies the readback hash. If
the journal says the run stopped during read-only preflight, it verifies the
full image without writing to the board. It then advances the schedule over
every durable one-shot claim, including a row claimed just before the crash
whose trial may not have reached completion. No claimed row is retried. If the
board restoration or its hash check fails, `resume` remains blocked. `resume`
uses the journal's original configuration and continues at the next unclaimed
row; the original long CLI need not be reconstructed.

The shared local lock is
`~/.local/state/wasmhome-hil/hardware.lock`, mode 0600, and is taken exclusively
for both #20 and #22 flash operations. Evidence, plan, journal, claims and
flash snapshots are kept in a user-owned campaign directory with mode 0700;
files are created mode 0600. Journal updates use a same-directory temporary
file, `fsync`, atomic rename and parent-directory `fsync`.

## Trial and restoration behavior

For each row the orchestrator writes and syncs an exclusive attempt claim before
touching the board. It verifies the full flash still equals the accepted #20
image, restores that image, overlays the selected build's matching
bootloader at 0x0 and its bootstrap app into both app slots, then verifies the
bootloader readback before booting it. The existing baseline partition table
is retained because its exact map was validated before any write. Provisioning uses only the ordinary signed OTA sequence-2
request and the verified HTTPS package. It never calls `write_flash` for the
NVS offset. NVS is read-only evidence: after the OTA sequence, esptool completes
all flash access, the board boots, and a fresh boot ID is sampled for the
sanitized preflight. One `resilience_hil_runner.py run` invocation then
executes the claimed row and the before/after HTTPS snapshots are correlated
against that run. Every row's `finally` path writes the accepted 16 MiB image
back and verifies the full readback hash.

Each snapshot and raw serial/UDP receipt remains in the private output tree.
The journal separates `restore_required`, `next_index`, row results, and claim
history so recovery can distinguish a durable completion from a crash between
flash writes and the journal update. If recovery is needed, restore/verify the
baseline first, then resume. If the journal is unreadable, do not delete claims
or plan files; retain the campaign tree for investigation and start a new
campaign only after the board has been restored from the #20 accepted image.

## Rollback bootloader and private rebuilds

The accepted #20 image contains a bootloader with app rollback disabled. A
native app built with rollback enabled cannot safely complete an OTA under
that bootloader: the image stays `ESP_OTA_IMG_NEW` instead of entering
`ESP_OTA_IMG_PENDING_VERIFY`. The signed-update reconciler continues to reject
`IMG_NEW`; no firmware acceptance rule is weakened. Every #22 row therefore
uses the bootloader produced by its own app build. Native requires rollback
enabled. Interp/AOT update modules and may retain rollback disabled, provided
the app sdkconfig, embedded marker and bootloader config all agree. Full 16 MiB restoration reinstates the exact accepted
bootloader, app slots, partition table and NVS after the row. The restore
leaves the board in the ROM loader so baseline runtime cannot mutate NVS
between rows.

After merging the final #20 source, rebuild four ESP32-S3 apps in distinct
build directories: native bootstrap v1, native OTA candidate v2, module-interp
bootstrap and module-aot bootstrap. The three bootstrap apps need the new V2
marker and final timeout/endpoint/source. Native v2 must retain the same
rollback, test hooks, timeout, trust and network settings as native v1, changing
`APP_PROJECT_VER` and `WASMHOME_UPDATE_RELEASE_VERSION` from v1 to v2. Keep
native `WASMHOME_CONTROL_VERSION=1` for the resilience protocol in both builds. Each
build must use its own sdkconfig with the corresponding rollback mode (native
requires `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`), 16 MiB flash, the repository
partition table, the frozen timeout, the selected
resilience test mode, and the verified CT endpoint/CA on port 18445. CMake now
rejects rollback-disabled native #22 configs and mismatched normal/fixture
endpoints, then embeds both endpoints and the exact sdkconfig SHA-256
in each V2 app marker. Retain the completed build's `bootloader/bootloader.bin`
and `bootloader/config/sdkconfig.h` together with the app and sdkconfig.
Generate a new private manifest directly from those build directories:

```sh
python3 tools/issue22_profile_manifest.py \
  --native-build /private/build-issue22-native \
  --interp-build /private/build-issue22-interp \
  --aot-build /private/build-issue22-aot \
  --source-commit <final-40-hex-source-commit> \
  --tls-ca /private/pki/ca.pem \
  --output /private/campaign/issue22-profiles-v2.json
```

Segment loads must also fit wholly inside one pinned IDF v5.2.6 bootloader
linker RAM area: DRAM `[0x3fce3700,0x3fce7700)` or contiguous IRAM
`[0x403c9700,0x403d3700)`. The logical IRAM/loader split at `0x403cc700`
is allowed inside a segment because `elf2image` can merge adjacent IRAM loads.
Zero/unaligned addresses, 32-bit address overflow, crossing a linker window,
peripheral/flash/other RAM destinations and overlapping loads fail closed.
Overlap checks normalize the SRAM instruction/data bus alias offset before
comparing ranges; adjacent non-overlapping segments remain valid. These bounds
come from the pinned `bootloader/subproject/main/ld/esp32s3/bootloader.ld`, so
changing IDF or its linker layout requires reviewing the validator as well.

The generated bootloader header is parsed as the flat IDF output format:
comments are removed while preserving quoted strings; duplicate macros,
conditionals, includes, undef directives, line continuations and malformed
input fail closed. A rollback define inside a block comment is ignored, and a
conditional inactive define cannot establish rollback support. Image integrity
checks do not themselves prove rollback semantics: the app/config/bootloader
hashes must still come from the same trusted build, followed by physical
native activation through `PENDING_VERIFY`/`VALID`.

`tools/hil_bootstrap_validation.py` performs these bounded checks with the
Python standard library, without importing a serial API, opening a port or
contacting CT. An offline esptool `image_info` inspection is also read-only,
but its success exit code alone is insufficient: the pinned esptool prints
invalid checksum/digest findings without necessarily failing the command.
The campaign validator explicitly compares both values and exact image size.

The generator hashes the four artifacts per bootstrap build, checks the app
marker against the sdkconfig and the two endpoints, and validates both rollback
configs and the complete
manifest before writing it. It opens no serial port or network listener. The
hash manifest records build provenance; it must be generated from trusted,
completed local builds rather than assembled from unrelated bootloader files.
The HIL coordinator snapshots all four artifacts and binds the manifest hash
to its journal. Create a new signed six-artifact package containing the new
native v1/v2 and the verified module v1/v2 payloads. Update the native release
hash and size in `resilience_hil_runner.EXPECTED_RELEASE_ARTIFACTS` to the exact
new v2 image; preserve module hashes only when their bytes still match.

Changing the server port does not alter signed module envelopes or negative
fixtures: their manifests contain campaign, version, sequence, payload digest
and AOT identity, without an endpoint. The existing immutable module payloads
and nine negative fixtures may be reused if campaign ID, trusted/untrusted
keys, AOT identity and sequence plan remain identical and verification passes.
The negative fixtures need not contain the currently active native v2 image;
they must fail at the documented signature/hash/sequence stage without
activation. Re-sign or regenerate affected envelopes/catalogs if any of those
identities change. The existing sequence plan is old=1 and next=3 for all
scenarios, after ordinary signed OTA establishes floor=2.

Service-module and Wasm trap artifact provenance also binds the clean source
revision. Refresh these generators' receipts after the final source commit
before building, even if deterministic payload bytes remain unchanged. Keep
the signed campaign ID fixed unless there is a reason to change its ledger
namespace; a fresh HIL output directory and plan do not require a different
signed artifact campaign ID. A campaign-ID change must also update the firmware
configs, runner and NVS preflight constants, then re-sign all provisioning and
fixture envelopes consistently.

Run static `check` with the V2 manifest, signed set, nine-fixture catalog, frozen
timeout proof and exact accepted baseline before starting a fresh campaign.
Do not reuse earlier profile BIN markers, claims or journal directories.

## User-level CT HTTPS process

The dedicated Ed25519 SSH key is already enrolled once in the `wasmhome`
account with the OpenSSH `restrict` option. This disables PTY allocation,
agent/X11/port forwarding and user SSH startup scripts while retaining the
command execution and file transfer needed by the orchestrator. Do not enroll
the same key again or replace the account's other authorized keys. The private
key stays on the local machine with mode 0600; the CT account's `.ssh` directory
and `authorized_keys` have modes 0700 and 0600 respectively. The provisioned
account runs as an ordinary UID and belongs only to its own group.

The 2026-10-17 access audit verified an unattended connection with the pinned
host key, exactly one matching restricted enrollment, the file ownership and
modes above, Python availability, and ownership of the campaign root. Its full
receipt remains in the private campaign records. No password, root login,
privileged group, system service or interactive shell is required by this
connection. A management route through Tailscale may use the same pinned CT
host-key alias; the firmware HTTPS endpoint must still use an address that the
ESP32-S3 can reach directly on its own network.

The orchestrator stages the strict fixture handler, its verifier, the signed
package, public verification keys, and the TLS files beneath a unique
user-owned directory under
`/home/wasmhome/.local/share/wasmhome-hil/issue22/`. It validates the combined
allowlist with `--check`, then starts its own Python HTTPS process in the
foreground-detached `nohup` pattern over strict SSH as `wasmhome`. The listener
binds only to the configured CT IPv4 address and port 18445. Its HTTP log is
0600 in the same 0700 campaign directory.

At startup it first reads any previous PID receipt for this campaign. It sends
TERM only if the PID, Linux process start-time and exact orchestrator server
script path all still match. A mismatch fails closed without overwriting the
receipt. The HTTPS server process itself writes the receipt atomically and
syncs it before constructing or binding its socket. Therefore, a crash between
launch and readiness either leaves a verifiable PID/start-time receipt for
`recover` to stop, or happens before the server can open the port. A different
process occupying 18445 also causes the new listener to fail; no system unit,
old campaign, or other process is stopped. On ordinary completion the same
identity check stops the listener. After a crash,
`recover` attempts this cleanup; CT unavailability does not block local board
restoration, and the journal records whether remote cleanup succeeded. Running
`resume` later performs the same exact-process cleanup before relaunching the
campaign listener.

There is no `systemctl`, `sudo`, linger or daemon prerequisite. The listener
starts when an HIL run/resume starts and stops when that invocation ends. If a
different user-owned listener has the port, resolve that outside the campaign
without interrupting it, then rerun `resume`.
