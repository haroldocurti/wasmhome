For source `8b3bddd729996853d212b9f678c2b6c6fb4d949f`, the physical run failed in AOT before benchmark CSV output. The closed capture records repeated `LoadProhibited` exceptions at PC `0x420b0fae`, with exception address `0x81006136`; no AOT workload samples were accepted. The captured AOT log SHA-256 is `be30587d082129cd15024ac38e9375f2b1c06300304e418cc69aee800cd84fb4`.

The independent offline AOT review used the exact module payload hash `c4c94777e5f9460b8e60065d5cb89c7e79907cac61720a61f5ebd5467b512d88` and Xtensa object hash `5f030fce3499b11a85b47f4166c0148347938af218405f7581fdb2ec44cd7b3f`. The object begins with bytes `36 61 00 81 ff ff 88 08`: `entry`, a placeholder `L32R`, then `L32I`. Based on the module layout, the first relocation is `R_XTENSA_SLOT0_OP` against `.literal`, addend zero, and the expected patched immediate is `0xfff6`; the placeholder `0xffff` instead targets the code entry whose first word is `0x81006136`. This matches the observed exception address.

This initial payload/panic comparison is a strong consistency check, not proof of which runtime state occurred. The loader guard conditions are satisfied by the object’s relative ELF type and non-null code pointer, and the relocation group is present. At that stage, the payload/panic evidence alone could not distinguish an absent relocation write from stale instruction fetch. A subsequent audit of the actual linked Xtensa object confirmed that strict-aliasing optimization removed the aligned immediate write in the original helper. The `.3` candidate replaces that helper with aligned 32-bit read-modify-write operations; host tests and an isolated target compile passed. Its runtime effect remains pending a new firmware build and physical trial. See the [separate port3 diagnosis and review](../../aot-alias-fix-2026-10-14/README.md); issue #9 remains open.

Its prior diagnosis must not be merged with this `LoadProhibited` failure, and the different signature here does not by itself prove the earlier cache issue is eliminated in every path.
