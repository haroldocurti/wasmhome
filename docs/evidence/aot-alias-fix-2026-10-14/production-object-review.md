# AOT Xtensa relocation helper: strict-aliasing investigation

**Finding:** the production AOT object at source 8b3bddd contains a compiled `R_XTENSA_SLOT0_OP` path that skips the immediate write for the aligned-field case used by the failing module. The build uses effective `-O2` with GCC strict aliasing enabled. A target-compiler differential compile changes only strict-aliasing behavior and emits the expected aligned store. This establishes a concrete compiler/codegen defect in `put_imm16_to_addr`; it is a strong explanation for the unpatched L32R immediate in the AOT panic. A fixed firmware has not yet been built or run, so the runtime correction is not physically confirmed and the overall issue remains open.

## Build identity and flags

The inspected artifact is the AOT build from commit `8b3bddd729996853d212b9f678c2b6c6fb4d949f`, tree `db38a2b261c2ebcc259a362eb7c8b3d589e56009`, ESP-IDF 5.2.6 revision `9ef24e3e2a2c96e720d83c574a3f8699177573da`. `compile_commands.json` has SHA-256 `011e75e38167785ac2b1f15aaed1450392f24cdcf18307ecd69164ac8774839b`; the sole entry for `aot_reloc_xtensa.c` uses Xtensa GCC 13.2.0 `esp-13.2.0_20250707` and has optimization options `-O3 -O2`, in that order. No `-fno-strict-aliasing` option is present. The same compiler queried with `-Q --help=optimizers -O3 -O2` reports both `-fstrict-aliasing` and `-fipa-strict-aliasing` enabled; the last optimization flag is `-O2`.

The exact compile command, with only output and dependency destinations redirected to a private scratch directory, reproduced the build object byte-for-byte: SHA-256 `ee2195283e656ed97822ebb76ab2a41bd517c578463b11d07f40fbab136e18e4`. The object is also the byte-identical member in the runtime archive (`34e96013d51b5eb300dcb049c3be4a7a9b82bee04f33185b28741c2e1203e3e1`), and the AOT link map (`439267b51e451cf4c37d701d3d5a04e0da7745de69b7605213a8aa585b2afcf1`) lists that archive member. The linked AOT ELF hash is `0d4aaedf57d1956fe40abdcaa1fcd01362d8c71e660639eee2dbb33758add699`. Thus the inspected object is from the actual linked build, not just a source-only reconstruction.

## Actual target disassembly

The source helper declares `int8 bytes[8]`, then accesses this declared character array through `int32 *` and `int16 *` lvalues for the normal aligned case. Those typed accesses violate the C strict-aliasing/effective-type rules. The normal branch intends to copy a word into `bytes`, replace two bytes, then copy the modified word back.

In source-annotated disassembly of the actual build object, `apply_relocation` calls `os_get_dbus_mirror`; at offsets `0xed` and `0xef` it computes and masks the immediate-field pointer. The branch at `0xf2` is `bnei a8, 3, 13c`, where `0x13c` is the function’s successful `return true`. The non-crossing path therefore returns without writing the mirror. The only subsequent scratch writes (`s32i`, `s8i`) and `memcpy` call are in the path where the immediate field crosses the four-byte boundary. The object does not emit a normal-path store. Full disassembly is saved in `apply-relocation-objdump.txt` (SHA-256 `29a3b7716f67473c0c7adcf432fb3cb799e64152380729f76a27d9154108785c`).

The module payload used in the failed trial has SHA-256 `c4c94777e5f9460b8e60065d5cb89c7e79907cac61720a61f5ebd5467b512d88`; its first text relocation is `R_XTENSA_SLOT0_OP` at offset 3 against `.literal`, addend 0. The failing PC `0x420b0fae` corresponds to code entry `0x420b0fa8` plus six bytes (the following `L32I`). For the L32R at code offset 3, the immediate field is at code offset 4 and hence address modulo four is 0. The IBus/DBUS mirror offset is a multiple of four, so the field remains on the non-crossing path. The relocation should set immediate `0xfff6` (relative target −40 bytes); the input placeholder is `0xffff`. With the write skipped, the placeholder L32R reads the first code word `0x81006136`, matching the recorded `EXCVADDR` at the subsequent L32I. This is consistent with the new LoadProhibited failure.

## Differential compile

I reran the same exact compile_commands entry with output and dependency files redirected, and appended only `-fno-strict-aliasing`. The variant object SHA-256 is `f88cff9debe13d653fb05380677ec20f188be457e2b0f25f4af4c8200b690817`; it was not linked into firmware or executed on hardware. In this target object, `apply_relocation` calls `put_imm16_to_addr`; the helper’s `addr % 4 != 3` path explicitly loads the aligned word, emits `s16i` into the scratch bytes, reloads the modified word, then emits `s32i` back to the aligned address. The crossing path remains separate and uses `memcpy`. Full variant disassembly is saved in `apply-relocation-no-strict-objdump.txt` (SHA-256 `71cca1d4e24aa87ce07c48c76617976edb02ad57c5802200294311d050dd31d4`).

A minimal host run of the same helper pattern corroborates the target result: with GCC 16.2.1, `-O3 -O2 -fstrict-aliasing` leaves `0x11223344` unchanged instead of writing `0x1122fff6`; with `-fno-strict-aliasing`, it writes the expected value. Host result details and source hash are in `host-repro-results.txt`. The target compiler differential is the stronger evidence.

## Conclusion and limits

The current object’s aligned relocation path omits the DBUS write, and strict-aliasing settings explain the compile-time difference. This is not merely a cache hypothesis: the current build fails before the write that should change the L32R immediate. It provides a concrete mechanism consistent with the AOT crash. A corrected implementation should use defined byte-wise/mask-shift operations (or another alias-safe read-modify-write) and retain an aligned-offset regression test; the active code fix is being handled separately. This report does not claim a successful corrected build or physical acceptance, and it does not replace the separate historical cache-disabled failure analysis.

No repository files, firmware outputs, IDF build trees, or device state were changed. The only target-side write was one isolated component-object differential compile under the toolchain’s private provenance area; neither variant was linked or run. No serial, UDP, reset, flash, or hardware action occurred.
