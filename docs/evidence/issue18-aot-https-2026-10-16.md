# Issue #18: signed HTTPS update of an AOT control module

AOT05 is the primary physical result for this change. On the ESP32-S3, the signed HTTPS update replaced control module v1 with v2 in one observed boot while the telemetry module retained the same generation and SHA-256. The strict offline analyzer passed all 24 checks. The attempt used the shared bounded telemetry-lock wait added after the issue 17 interpreter run exposed a shortfall in telemetry coverage; AOT04 remains accepted historical evidence, and AOT05 validates the AOT profile after the shared change. The interpreter physical rerun belongs to issue 17.

The reviewed AOT image was built from source revision `1e54b1128cf083fb2c000dfd6d79303a5467fef7` with the pinned ESP-IDF 5.2.6 toolchain. It is 1,036,640 bytes with SHA-256 `7513104cf7afcc709d5b04ae325e7921388e1e48ade5980caa94b80672ebeaa2`. Image validation and the allocator ABI check passed for both the WAMR runtime and manager. The effective AOT/interpreter configurations matched the previously reviewed profiles. The canonical service-module manifest is `4ccd1944c65d58b08f6c013717a36ae283c73f6c2c244e868e0b8d1c5d62fedf`; all twelve generated outputs were rechecked, and the four signed control payloads matched the frozen HTTPS package byte for byte. Private build and review receipts are identified by digest in the [sanitized evidence JSON](issue18-aot-https-2026-10-16.json).

The integrated host suite on stack head `284363b` ran 168 tests: 167 passed and one Windows-only test was skipped. The wire-codec C library and PowerShell 7.6.6 were available for that run.

## AOT05 main update

The device accepted one update for scenario 3, component 1, sequence 2. The verified payload was received in full (1,256 of 1,256 bytes), SHA-256 `293d78b1af5e0c7e76593d9b8e755692ee311d8427c43d94673ddfd499d5bf53`. That digest matched the active v2 control module after activation and after releasing v1. The ledger committed and read back floor sequence 2. Control generation changed from 2 to 3; telemetry stayed at generation 1 with SHA-256 `e8c6e6ff9c7fc01445adc32b181d755252b99758c01af68970b51d6ad445ea63` in the accepted, activated, and old-control-released snapshots.

At 27 °C, the observer recorded 66 correct v1-high responses before acceptance and 211 correct v2-low responses after activation, with no v1 results after v2 activation. The update and its telemetry samples passed the same-boot correlation checks. Two power-on records occurred during UART setup before the observer started; the observer and all update events then remained on one boot, and the serial port was not reopened or reset during the observation window.

The update took 6.624 s from the observer trigger to the first valid v2 response. The gap between the last valid v1 response and first valid v2 response was 1.505 s, corresponding to an estimated 1.405 s of control unavailability after subtracting the 100 ms request period. The observer saw 903 valid telemetry samples and 885 valid control results, with 14 control timeouts and 8 late results. No sequence gaps remained unresolved. During the update interval, it received 66 telemetry samples against a minimum of 65; the largest interval was 160.223 ms against a two-cadence limit of 200.068 ms. The reported telemetry busy-drop counter did not increase.

Device phases use the monotonic MCU boot clock; service gaps use the observer's host clock. Representative device stage durations were: accepted to manifest download start 78.072 ms; manifest download 3,346.516 ms; manifest verification 276.048 ms; payload download and verification 948.336 ms; verified payload to staged 160.944 ms; candidate load 92.364 ms; instantiation 6.151 ms; candidate health check 2.597 ms; ledger commit and readback 67.406 ms; activation 1.274 ms; and old-control release 2.701 ms. The complete phase list is in the evidence JSON.

The API lock was held for 83.756 ms during activation: candidate load 11.107 ms, health check 0.409 ms, ledger commit/readback 66.342 ms, pointer swap 0.009 ms, and old-control release 1.658 ms. These MCU intervals are separate from the 1.505 s host-observed service gap. The 9 µs pointer swap is not end-to-end availability; deferred serial events still occupy the control worker before it handles later requests.

The lowest measured internal free heap was 139,719 B, with a largest free internal block of 43,008 B. Minimum measured PSRAM free heap was 8,082,796 B. The WAMR allocator reached a 259,432 B peak with zero allocation failures. At the first v2 control operation, the telemetry and control task high-water marks were 9,696 B and 6,624 B remaining. The firmware retains legacy field names ending in `_words`; on this ESP-IDF 5.2.6 Xtensa target, `StackType_t` is one byte, so these values are bytes. Heap values are phase snapshots, not global allocation peaks.

## Persistence smoke and restoration

A separate 20-second, no-trigger smoke after a new boot observed 199 valid v2 control responses and 203 telemetry samples, with zero control timeouts and zero unresolved sequence gaps. It recorded the expected v2 outputs at 23 °C (low, 67 responses), 27 °C (low, 66), and 32 °C (high, 66). This demonstrates functional persistence of v2 across a new boot. It does not read back the floor or payload hash after that boot; sequence 2 and the active hash are proven by the main update's commit/readback and activation checks.

After the accepted main run and smoke, the complete 16 MiB flash was restored and read back. The baseline and readback SHA-256 both equal `b66c24a3514be56702c1cf7f8d2116e44d5fe0475e3c3c67b65850258eb18ae3`; the full image and all eight flash-region comparisons matched. An independent review confirmed the byte-for-byte result, and the board was left in the bootloader. Physical recovery from an injected failure was not exercised.

## Earlier attempts and AOT04 history

AOT04, built from revision `e327401407fde799f555261ec7921969fcdf35bf`, remains an accepted 24/24 physical run. It recorded 65 telemetry samples during the update, exactly the required minimum, with a 141.993 ms largest telemetry interval and no increase in the sampled busy-drop counter. It is retained as historical evidence; AOT05 is the primary result because the later shared bounded-wait change required both modular profiles to be revalidated.

The issue 17 interpreter attempt 01 then missed the strict telemetry interval requirement by one sample (49 of 50) and recorded three busy drops during brief API-lock contention. The shared firmware now waits for telemetry lock contention for at most one 100 ms period, while retaining WAMR serialization and counting timeouts. AOT05 passed the unchanged strict analyzer with this behavior. The earlier AOT attempts 01 and 02 remain rejected: 01 stopped before sending a trigger at the allocator callback ABI boundary; 02 was split across two boot IDs by a reset after observer start and also failed telemetry coverage. Attempt 03 was only a pre-read and stack-gate preparation, with no firmware write or trigger.

Raw UART, observer captures, flash snapshots, configuration, packet captures, and network credentials remain in private storage. This report publishes only reviewed metrics and cryptographic digests; it does not claim post-reset floor/hash readback or physical recovery behavior.
