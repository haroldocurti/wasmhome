# Issue #18: signed HTTPS update of an AOT control module

The ESP32-S3 completed a real signed HTTPS update of the AOT control module from v1 to v2 in one boot. The strict offline analyzer passed all 24 checks. The verified 1,256-byte payload SHA-256 matched the active v2 control hash, the control generation advanced from 2 to 3, and the persistent ledger reported floor sequence 2 after commit. Telemetry stayed at generation 1 with the same SHA-256 before, during, and after the swap.

The AOT image was built from source revision `e327401407fde799f555261ec7921969fcdf35bf` with the pinned ESP-IDF 5.2.6 toolchain. The 1,036,496-byte image has SHA-256 `798d7248e5fb85759b7049dbca923798e9455ffb869b415b8da99418af33b697`; image validation and the WAMR allocator ABI check passed for both runtime and manager. The private build and stack-review receipts are committed by digest in the [sanitized evidence JSON](issue18-aot-https-2026-10-16.json).

The signed v2 payload was received in full (1,256 of 1,256 bytes), with SHA-256 `293d78b1af5e0c7e76593d9b8e755692ee311d8427c43d94673ddfd499d5bf53`. The analyzer matched that digest to the active control at activation and after releasing the old module. The 27 °C behavior distinguished the releases: 66 valid v1 responses were GPIO high before acceptance, followed by 211 valid v2 responses GPIO low after activation; there were no v1 results after v2 activation.

The external observer recorded 902 valid telemetry samples and 885 valid control results. It also recorded 14 control timeouts and 8 late results; these service losses remain part of the result. The largest gap from the last valid v1 response to the first valid v2 response was 1.506 s, corresponding to an estimated 1.406 s of control unavailability after subtracting the 100 ms request period. No sequence gaps remained unresolved. During the 6.624 s acceptance-to-first-v2 interval, the observer received all 65 telemetry samples required by the baseline cadence. The median telemetry cadence was 100.095 ms, the largest interval gap was 141.993 ms against a 200.190 ms limit, and the sampled runtime busy-drop counter did not increase.

Device phase times use the MCU boot clock; observer service intervals use a separate host monotonic clock. Within the device control transaction, the API lock was held for 81.642 ms: candidate load 11.090 ms, health check 0.414 ms, ledger commit and readback 64.246 ms, pointer swap 0.008 ms, and release of the old control module 1.645 ms. These internal phase timings do not represent end-to-end service availability. In particular, the 8 µs pointer swap is not the observed service gap; deferred serial event emission still occupies the control worker before it can process later requests.

The lowest measured internal free heap was 139,695 B, with a largest free internal block of 41,984 B. The lowest measured PSRAM free heap was 8,082,796 B. The WAMR allocator reached a 259,432 B peak and reported zero allocation failures. At the first v2 control operation, telemetry and control task high-water marks were 9,696 B and 6,780 B remaining. The firmware retains legacy field names ending in `_words`; on this ESP-IDF 5.2.6 Xtensa target, `StackType_t` is one byte, so these reported counts are bytes. Heap values are phase snapshots, not total memory cost or global allocation peaks.

A separate 12-second, no-trigger smoke after a new boot observed 119 valid v2 control responses, 122 telemetry samples, zero control timeouts, and zero unresolved sequence gaps. It recorded the expected v2 outputs at 23 °C (low, 40 responses), 27 °C (low, 39), and 32 °C (high, 40). This establishes functional persistence of v2 across a new boot. The smoke did not read back the ledger floor or payload hash after that boot; those values are proven by the main update's commit/readback and active-hash checks. Physical recovery from an injected failure was not exercised.

The earlier attempt 01 failed before sending a trigger at the allocator callback ABI boundary. Attempt 02 performed an update but was rejected by the strict analyzer because a reset after observer start split its capture across two boot IDs and the telemetry interval failed coverage. Attempt 03 was a pre-read and stack-gate preparation only; it made no firmware write, reset, or trigger. Their raw evidence remains private and none of their measurements is included above.

After the accepted main run and smoke, the full 16 MiB device flash was restored and read back. The baseline and readback SHA-256 both equal `b66c24a3514be56702c1cf7f8d2116e44d5fe0475e3c3c67b65850258eb18ae3`; an independent byte-for-byte comparison passed, all eight flash-region comparisons matched, and the board was left in ROM. Private analyzer, observer, UART, build, and restoration receipts are identified by SHA-256 in the JSON. Raw captures, configuration values, network addresses, flash snapshots, and packet captures remain private.
